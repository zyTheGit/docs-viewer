# 数据库高级指南

> 面向有生产环境经验、需要设计数据库架构的开发者。覆盖连接池与读写分离、缓存一致性、并发控制、多租户、分库分表与数据归档等架构级话题。

## 1. 连接池与生产配置

### 1.1 池参数调优

```typescript
TypeOrmModule.forRootAsync({
  useFactory: (configService: ConfigService) => ({
    // ...连接信息
    extra: {
      max: 20,                       // 最大连接数
      min: 5,                        // 最小保活连接
      idleTimeoutMillis: 30000,      // 空闲回收
      connectionTimeoutMillis: 5000, // 建连超时
      statement_timeout: 10000,      // 语句超时（pg）
      query_timeout: 10000,
    },
    retryAttempts: 3,
    retryDelay: 1000,
    logging: ['error', 'warn'],      // 生产只记录慢查询/错误
  }),
})
```

### 1.2 连接数怎么算

- 应用侧：`max × 实例数 ≤ 数据库 max_connections × 70%`
- 数据库连接是稀缺资源，多实例部署时每个实例的池要**缩小**
- 网关层报 `too many connections` 时，优先检查池配置而不是无脑加大

## 2. 读写分离与多数据源

### 2.1 原生 Replication 配置

```typescript
TypeOrmModule.forRoot({
  type: 'postgres',
  replication: {
    master: {
      host: 'master.db.internal',
      username: 'app',
      password: '***',
      database: 'app',
    },
    slaves: [
      { host: 'replica1.db.internal', username: 'app', password: '***', database: 'app' },
      { host: 'replica2.db.internal', username: 'app', password: '***', database: 'app' },
    ],
  },
  autoLoadEntities: true,
})
```

> ⚠️ TypeORM 会把**所有读查询**路由到 slaves，但事务中的读写仍在 master。要警惕**主从延迟**：写后立即读的场景必须强制走 master。

### 2.2 强制读主

```typescript
// 方式一：把读包进事务（事务默认走 master）
await this.dataSource.transaction(async (manager) => {
  return manager.findOne(User, { where: { id } });
});

// 方式二：关键接口直连 master 数据源
@BuilderClassDataSource('master')  // 或注册第二个 DataSource
```

### 2.3 多数据库（多 DataSource）

```typescript
// 注册
TypeOrmModule.forRoot({ name: 'default', ... }),
TypeOrmModule.forRoot({ name: 'analytics', ... }),

// 使用
@InjectDataSource('analytics') private analyticsDs: DataSource,
```

## 3. 缓存与数据库一致性

### 3.1 TypeORM 内置查询缓存

```typescript
// 单查询缓存
this.usersRepository.find({ where: { isActive: true }, cache: 60000 });

// 命名缓存，可主动失效
this.usersRepository.findOne({ where: { id }, cache: { id: 'user_1', milliseconds: 300000 } });

// 失效
await this.queryResultCache.remove(['user_1']);
```

### 3.2 Cache-Aside 模式与一致性

业务缓存（Redis）推荐 **先更新库，再删缓存**，并配合双删与 TTL 兜底：

```typescript
async updateUser(id: string, dto: UpdateUserDto) {
  await this.usersRepository.update(id, dto);      // 1. 更新库
  await this.cache.del(`user:${id}`);              // 2. 删缓存
  // 兜底：TTL 兜住所有极端不一致窗口
}
```

进阶：**延迟双删**（删缓存 → 更新库 → 延迟几百毫秒再删一次）应对"更新期间并发读把旧值写回缓存"。

> 一致性铁律：缓存永远只是加速层，必须接受"短暂不一致"；任何方案失效时，TTL 是最后一道防线。

## 4. 并发控制

### 4.1 乐观锁（默认首选）

```typescript
@VersionColumn()
version: number;

// update 时自动带 WHERE version = ?，冲突抛 OptimisticLockVersionMismatchError
await this.repo.update(id, { stock: newStock });
```

适合：冲突概率低、重试成本小（大多数业务）。

### 4.2 悲观锁（热点数据）

```typescript
await this.dataSource.transaction(async (manager) => {
  const product = await manager
    .createQueryBuilder(Product, 'product')
    .setLock('pessimistic_write')     // SELECT ... FOR UPDATE
    .where('product.id = :id', { id })
    .getOne();

  product.stock -= qty;
  await manager.save(product);
});
```

适合：秒杀扣库存、余额等强竞争场景。锁范围越小越好，事务越短越好。

### 4.3 原子更新（无锁化）

```typescript
// 不读出来再写回，直接在 SQL 层原子扣减，天然防超卖
const result = await this.dataSource
  .createQueryBuilder()
  .update(Product)
  .set({ stock: () => 'stock - :qty' })
  .where('id = :id AND stock >= :qty', { id, qty })
  .execute();

if (result.affected === 0) throw new BadRequestException('库存不足');
```

> ✅ 优先级建议：**原子 SQL > 乐观锁 > 悲观锁**，能用更轻的方案就不要上重锁。

## 5. 多租户设计

三种隔离级别：

| 方案 | 实现 | 隔离性 | 成本 |
|---|---|---|---|
| **共享表**（tenant_id 列） | 全表加 tenant_id | 低 | 最省 |
| 独立 Schema | 一租户一 schema | 中 | 中 |
| 独立数据库 | 一租户一库 | 最高 | 贵 |

### 5.1 共享表方案：全局 Scope

利用 TypeORM 的 `Read/Write QuerySubscriber` 或自定义 Repository 实现**强制注入 tenant_id**，杜绝业务代码漏写：

```typescript
// 方式一：实体级别钩子（简单场景）
export class TenantSubscriber implements EntitySubscriberInterface {
  listenTo() { return TenantEntityBase; }

  beforeInsert(event: InsertEvent<TenantEntityBase>) {
    event.entity.tenantId = event.manager.data?.tenantId;  // 通过 CLS 传入
  }
}
```

```typescript
// 方式二：基于 AsyncLocalStorage 的请求上下文
@Injectable()
export class TenantContext {
  get tenantId(): string {
    const ctx = als.getStore();
    if (!ctx?.tenantId) throw new Error('missing tenant context');
    return ctx.tenantId;
  }
}
```

```typescript
// 中间件里写入租户上下文（来自 JWT / 子域名 / Header）
app.use((req, res, next) => {
  als.run({ tenantId: req.user?.tenantId }, next);
});
```

> ⚠️ 多租户共享表的两大事故源：**查询漏加 tenant_id**（越权读取）与**唯一索引没带 tenant_id**（A 租户数据阻塞 B 租户）。唯一索引一律 `UNIQUE(tenant_id, xxx)`。

## 6. 大数据量治理

### 6.1 流式读取（不再全量 load）

```typescript
// ❌ find() 会把百万行全部加载进内存
// ✅ 流式游标
const stream = await this.dataSource
  .createQueryBuilder(User, 'user')
  .stream();

stream.on('data', (row) => processRow(row));
stream.on('end', () => done());

// 或分批迭代
await this.dataSource
  .createQueryBuilder(User, 'user')
  .orderBy('id')
  .take(1000)
  .offset(...)
  // 更好的做法：基于游标（keyset）分页
```

### 6.2 深分页优化（keyset 分页）

```sql
-- ❌ OFFSET 1000000：要扫过前 100 万行
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000000;

-- ✅ 基于游标：直接定位
SELECT * FROM orders WHERE id > $lastId ORDER BY id LIMIT 20;
```

```typescript
async findByCursor(lastId: string, size = 20) {
  return this.ordersRepository
    .createQueryBuilder('order')
    .where('order.id > :lastId', { lastId })
    .orderBy('order.id')
    .take(size)
    .getMany();
  // 返回时带上 items 的最后一个 id 作为 nextCursor
}
```

### 6.3 冷热分离与归档

- 冷数据（超过 N 个月）定期归档到历史表/对象存储，主表保持精瘦
- 用 `pg_partman` 分区表按月分区，或业务层按 `created_at` 路由查询
- 统计类查询走读库/数仓，别在主库跑大聚合

## 7. 分库分表（超大流量才考虑）

在动手分片前，按顺序考虑：**索引优化 → 读写分离 → 归档分区 → 缓存**，这些能解决 95% 的问题。

若确实需要分片：

| 维度 | 选择 |
|---|---|
| 分片键 | 最高频查询字段（如 user_id），宁可冗余也要保证常用查询单分片命中 |
| 垂直分库 | 按业务域拆（订单库/商品库/用户库），配合微服务边界 |
| 水平分表 | 按 hash(range) 拆表，如 `orders_00` ~ `orders_63` |
| 中间件 | 应用层多 DataSource + 路由策略，或外部 Proxy（Vitess/ShardingSphere） |

**分片代价**：跨片 JOIN/事务消失、全局 ID 需要分布式方案（雪花 ID）、扩容需要数据迁移。每个都必须提前设计。

## 9. 架构决策清单（Checklist）

上线前自检：

- [ ] `synchronize` 已关闭，所有表结构变更走迁移
- [ ] 连接池按实例数收敛，配置了超时
- [ ] 所有高频查询有索引，`EXPLAIN` 无全表扫描
- [ ] 热点写路径使用原子更新，无读改写竞态
- [ ] 缓存有 TTL 兜底，写路径遵循"更新库后删缓存"
- [ ] 多租户唯一索引包含 tenant_id，上下文强制注入
- [ ] 大表有归档/分区策略，深分页用 keyset
- [ ] 慢查询日志与连接池监控已接入

## 10. 本篇小结

- ✅ 连接池：max/min/超时三参数，池大小按实例数全局收敛
- ✅ 读写分离：能省读压力，但要处理主从延迟与强制读主
- ✅ 缓存一致性：Cache-Aside + 删缓存 + TTL 兜底
- ✅ 并发：原子 SQL 优先，乐观锁其次，悲观锁只给热点
- ✅ 多租户：Scope 强制注入 + 唯一索引带 tenant_id
- ✅ 大数据量：流式读取、keyset 分页、冷热分离，分片是最后手段
