# 消息队列实战

> 用 BullMQ 在 NestJS 中实现异步任务、延迟/重试、事件驱动与可靠投递。

---

## 1. 什么时候需要消息队列

| 场景 | 例子 | 队列带来的价值 |
|---|---|---|
| 异步削峰 | 发邮件、生成报表、视频转码 | 请求秒回，后台慢慢做 |
| 解耦 | 订单创建 → 库存/积分/通知 | 下游故障不影响下单 |
| 延迟任务 | 15 分钟未支付自动取消 | 天然支持定时触发 |
| 重试 | 调第三方 API 失败 | 自动指数退避重试 |
| 流量整形 | 爬虫抓取、批量导入 | 控制消费速率 |

NestJS 生态主力方案：

| 方案 | 适用 |
|---|---|
| **BullMQ**（`@nestjs/bullmq`） | Redis 支撑的通用任务队列，本篇主角 |
| Nest 微服务传输层 | Redis/NATS/Kafka/gRPC 进程间通信 |
| Kafka | 高吞吐日志流、事件溯源 |

## 2. BullMQ 快速上手

```bash
npm install @nestjs/bullmq bullmq
```

### 2.1 注册队列模块

```typescript
// app.module.ts
BullModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    connection: {
      host: config.get('REDIS_HOST'),
      port: +config.get('REDIS_PORT'),
    },
    defaultJobOptions: {
      attempts: 3,
      backoff: { type: 'exponential', delay: 2000 },  // 2s/4s/8s
      removeOnComplete: 1000,   // 保留最近 1000 条成功记录
      removeOnFail: 5000,
    },
  }),
}),
BullModule.registerQueue(
  { name: 'email' },
  { name: 'order-timeout' },
),
```

### 2.2 生产者：投递任务

```typescript
@Injectable()
export class EmailQueueProducer {
  constructor(
    @InjectQueue('email') private readonly emailQueue: Queue,
  ) {}

  async sendWelcome(userId: string, email: string) {
    await this.emailQueue.add(
      'welcome',                       // job 名
      { userId, email },               // payload（必须可 JSON 序列化）
      { jobId: `welcome:${userId}`,    // 幂等：同一用户不重复投递
        delay: 5000 },
    );
  }
}
```

### 2.3 消费者：Processor

```typescript
@Processor('email')
export class EmailConsumer extends WorkerHost {
  private readonly logger = new Logger(EmailConsumer.name);

  async process(job: Job<{ userId: string; email: string }>) {
    this.logger.log(`发送欢迎邮件 #${job.id} → ${job.data.email}`);

    if (Math.random() < 0.3) throw new Error('SMTP 临时故障'); // 模拟失败

    await this.mailer.send({
      to: job.data.email,
      subject: '欢迎加入',
      template: 'welcome',
    });
  }
}
```

> 💡 `process` 抛错 = 任务失败，BullMQ 按 `attempts`/`backoff` 自动重试，重试耗尽进入 failed 状态。

## 3. 延迟队列：订单超时自动取消

```typescript
// 创建订单时投递延迟任务
await this.timeoutQueue.add(
  'check-paid',
  { orderId },
  { delay: 15 * 60 * 1000,                       // 15 分钟后执行
    jobId: `timeout:${orderId}`,                 // 幂等防重复
    removeOnComplete: true },
);
```

```typescript
@Processor('order-timeout')
export class OrderTimeoutConsumer extends WorkerHost {
  async process(job: Job<{ orderId: string }>) {
    const order = await this.ordersRepository.findOneBy({ id: job.data.orderId });

    // 用户已支付：什么都不做（或校验投递时预置的取消标记）
    if (order.status !== 'PENDING') return '已处理，跳过';

    await this.ordersRepository.update(order.id, { status: 'CANCELLED' });
    await this.stockService.restore(order);       // 归还库存
  }
}
```

> 支付成功时可以调 `job.remove()` 提前移除超时任务，或依赖消费时的状态判断——**后者更稳**（消息不会丢状态机）。

## 4. 队列事件与监控

### 4.1 Worker 事件

```typescript
worker.on('failed', (job, err) => this.logger.error(`${job?.id} 失败: ${err.message}`));
worker.on('completed', (job) => this.logger.log(`${job.id} 完成`));
```

### 4.2 队列状态与告警

```typescript
@Cron(CronExpression.EVERY_5_MINUTES)
async checkQueueHealth() {
  const counts = await this.emailQueue.getJobCounts('waiting', 'failed', 'active');
  if (counts.failed > 100) {
    await this.alertService.notify(`邮件队列积压失败任务 ${counts.failed} 条`);
  }
  if (counts.waiting > 10000) {
    await this.alertService.notify(`邮件队列积压 ${counts.waiting} 条，考虑扩容 Worker`);
  }
}
```

## 5. Nest 微服务事件（对比参考）

进程间事件驱动，Nest 微服务传输层更贴合框架：

```typescript
// main.ts（混合应用：HTTP + 微服务）
const app = await NestFactory.create(AppModule);
app.connectMicroservice<MicroserviceOptions>({
  transport: Transport.REDIS,
  options: { host: 'localhost', port: 6379 },
});
await app.startMicroservices();

// 事件处理器
@Controller()
export class InventoryController {
  @EventPattern('order.created')
  async handleOrderCreated(data: { orderId: string; items: OrderItem[] }) {
    await this.inventoryService.deduct(data.items);
  }
}

// 发布事件
this.client.emit('order.created', { orderId, items });
```

> BullMQ 与微服务事件怎么选？**任务**（必达、可延迟、要重试）→ BullMQ；**事件**（通知下游）→ 微服务事件 / 事件总线；要**持久化事件流、高吞吐** → Kafka。

## 6. 可靠投递要点（面试高频）

| 问题 | 解法 |
|---|---|
| 生产者投递丢失 | 本地消息表：先写库记录，投递成功后标记；定时扫描补偿 |
| 消费者重复消费 | 任务幂等：业务键唯一约束 / `jobId` 去重 / Redis SETNX |
| 消息积压 | 扩容 Worker、按优先级分队列、限流保护下游 |
| 死信处理 | 重试耗尽后人工介入 + 告警，提供重新入队 API |
| 顺序性 | BullMQ 按分片 FIFO（`groupId`）保证，或单 key 单队列 |
| at-least-once vs at-most-once | BullMQ 是 at-least-once（崩溃会重投），所以**幂等是标配** |

## 8. 本篇小结

- ✅ BullMQ 三件套：`forRoot` 连接、`registerQueue` 建队列、`@Processor` 消费
- ✅ `jobId` 幂等 + 指数退避重试是默认姿势
- ✅ 延迟队列实现订单超时取消，靠**状态机判断**兜底
- ✅ 监控：`getJobCounts` 定时巡检 + Bull Board 面板 + 失败告警
- ✅ 可靠投递：本地消息表补偿、幂等消费、死信人工介入
- ✅ BullMQ（任务）vs 微服务事件（通知）vs Kafka（事件流）的选型边界
